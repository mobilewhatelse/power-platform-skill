# Power Platform Code Apps + Dataverse

This skill packages field-tested patterns for taking a Power Apps **Code App** (a React/Vite app generated by tools like vibe.powerapps.com, or built from scratch) from "in-memory mock data" to a real, production-ready Dataverse-backed solution — including schema provisioning, security, auditing, and solution packaging, all done directly against the Dataverse Web API rather than through the portal UI.

It contains no project-specific business content — only the mechanics of the platform.

## When to use this

- The user has a Code App (React/Vite, `power.config.json`, `src/generated/*`) they want to connect to real Dataverse tables instead of in-memory data.
- The user needs to create Dataverse tables/columns/relationships programmatically (faster and more repeatable than clicking through make.powerapps.com for dozens of columns).
- The user needs security roles, native Dataverse auditing, a model-driven app (sitemap/AppModule) alongside the Code App, or a clean exportable managed solution.
- The user hits a Code App deployment error (broken images, `power-apps push` failures, table deletion blocked, etc.) — see [references/troubleshooting.md](references/troubleshooting.md).

## Prerequisites

- Azure CLI (`az`) logged in as a user with at least **System Customizer** (ideally **System Administrator**) on the target Dataverse environment: `az login`.
- Node.js for running Web API provisioning scripts and for the Code App's own build tooling.
- PAC CLI (`pac`) for user/role assignment and solution import/export convenience commands — optional, most things are also doable via raw Web API calls.
- The environment must have **"Enable code apps"** turned on (Power Platform Admin Center → Environments → select environment → Settings) before a Code App can be pushed to it.

## Workflow

1. **Design the schema** — table list, columns, relationships, dependency order (tables with no lookups first). See [references/dataverse-web-api.md](references/dataverse-web-api.md).
2. **Provision Dataverse** — publisher, solution, tables, columns, relationships via raw Web API calls (idempotent scripts, re-runnable). Same reference.
3. **Wire the Code App to Dataverse** — flip data-source config from in-memory to Dataverse, regenerate/adjust generated hooks/models. See [references/code-app-deployment.md](references/code-app-deployment.md).
4. **Add security & governance** — real Dataverse security roles + native auditing instead of hand-rolled "governance tables". See [references/security-and-audit.md](references/security-and-audit.md).
5. **(Optional) Add a model-driven app** alongside the Code App for admin/ops screens backed by the same tables — sitemap + AppModule. See [references/model-driven-app.md](references/model-driven-app.md).
6. **Build & deploy the Code App** — `npm run build` then `npx power-apps push`. Watch for the static-asset bundling gotcha in [references/code-app-deployment.md](references/code-app-deployment.md).
7. **Package for production** — make sure the Code App, tables, roles, and sitemap all belong to one named solution; export a managed solution and verify it's self-contained. See [references/solution-alm.md](references/solution-alm.md).

Each reference file is self-contained with working request/response shapes and copy-pasteable script snippets — read the one relevant to the task at hand rather than all of them up front.

## Core principle: script the Web API, don't click through the UI

Every mutation in this skill (tables, columns, relationships, roles, privileges, audit flags, sitemaps, AppModule components, solution membership) can be done with a plain HTTP call:

```
<environment-url>/api/data/v9.2/<EntitySet or bound action>
```

authenticated with a short-lived bearer token from:

```bash
az account get-access-token --resource "https://<org>.crm.dynamics.com" --query accessToken -o tsv
```

Never persist that token to disk — fetch it fresh at the start of each script run (or cache it in memory with a naive expiry check). This means your provisioning scripts contain **zero secrets** and are safe to commit to source control as-is.

Write scripts to be **idempotent**: check for existing entities/columns/roles by name before creating, so the same script can be re-run safely after a partial failure.
